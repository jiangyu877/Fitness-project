## 1. 产品部职责

产品部只负责产品经理工作，不参与任何代码开发。职责包括：

- 定义产品目标、范围、用户、业务规则和明确排除项；
- 输出用户流程、状态机、页面需求和验收口径；
- 组织专业输入、风险规则、内容模板和固定文案的签字确认；
- 维护验收标准、优先级、依赖、风险、里程碑和发布门槛；
- 协调 UI 部与研发团队，处理需求冲突和变更；
- 组织原型评审、需求评审、验收和四周封闭测试复盘。

产品部不创建或修改应用源码、数据库迁移、鉴权实现、API 实现、前端页面、自动化测试或部署配置。

## 2. 部门边界

| 部门 | 负责 | 不负责 |
| --- | --- | --- |
| 产品部 | 规格、PRD、流程、状态、接口需求、验收、排期和协调 | 任何代码实现 |
| UI 部 | 移动 H5 与 Web 后台的信息架构、交互、视觉、原型和前端实现 | 后端业务规则、数据库和鉴权实现 |
| 研发团队 | 后端、数据库、鉴权、API、测试、部署及技术方案 | 擅自改变产品范围或专业规则 |
| 专业审核方 | 风险问卷、安全文案、饮食/训练内容和调整规则签字 | 产品排期和技术实现 |

产品部拥有并维护 `docs/superpowers/specs/` 与 `docs/superpowers/plans/` 中的产品文档。UI 部和研发团队各自声明并维护其实现目录；产品部不修改实现目录，也不参与双方的日常接口或联调同步。

## 3. 正式开工门槛

当前 `docs/superpowers/specs/2026-07-22-fitness-guidance-product-design.md` 标记为 v1.0，内容是可点击原型与人工服务验证；交接文档声称当前基线为 v2.0 封闭测试 MVP（移动 H5 + Web 运营后台）。两者范围冲突。

在完成下列事项前，产品部不向研发团队下达正式编码需求：

1. 找回或重建 v2.0 正式规格；
2. 逐条记录 v1.0 到 v2.0 的范围变化；
3. 明确审批人并完成产品评审；
4. 形成需求—页面—技术契约—验收覆盖矩阵；
5. UI 部与研发团队自行确认目录所有权和技术协作方式。

在此之前，允许 UI 部制作标明演示属性的原型，允许研发团队评估契约和技术风险，但不得把未确认业务规则当成正式需求。

## 4. 产品工作任务

### 任务 1：确认 v2.0 产品基线

**产品输出：**

- v2.0 产品规格；
- v1.0 → v2.0 变更记录；
- 范围清单与明确不做清单；
- 角色、权限、状态机和异常路径；
- 具名审批记录。

**验收：**产品范围、身份、计划状态边界、角色权限、数据留存、页面优先级和成功标准已由产品部冻结；筛查、专业内容和风险恢复规则由具名专业人员签字。

### 任务 2：冻结 MVP 用户旅程与页面需求

**产品输出：**

- 用户端：受邀账号密码登录、授权、筛查、建档、待确认计划、饮食/训练双确认、今日任务、每日记录、周反馈、调整说明、数据请求；
- 运营端：工作台、用户详情、风险事件、双审核、计划版本、周调整、数据请求、审计查询；
- 每个页面的进入条件、空态、加载态、阻断态、异常态和可执行动作；
- UI 文案原则：安全、清晰、非诊断，不把估算表述为精确事实。

**验收：**UI 原型中的每个状态都能映射到产品状态机，并有清晰的下一步。

### 任务 3：确认跨端产品行为

**产品输出：**跨端用户流程、业务状态、权限边界、异常处理和统一验收场景。

产品部只定义“用户在什么条件下可以做什么、系统应呈现什么结果”，不定义 API 路由、请求响应、错误码、数据库字段或技术契约。相关技术契约由 UI 部与研发部直接协作。

**验收：**UI 与研发对同一业务场景、状态变化和可观察结果理解一致；技术实现细节不进入产品部职责。

### 任务 4：完成专业输入清单

**产品输出：**

- 风险筛查题和排除条件；
- 固定安全提示与求助文案；
- 饮食模板、训练模板和周调整示例；
- 数据充分性规则和异常响应时限；
- 审核人、版本、审核日期和复审日期。

**验收：**专业材料签字前只允许使用 mock 数据，不得招募真实测试用户。

签字状态统一记录在 `docs/superpowers/specs/2026-07-23-professional-input-approval-checklist.md`。产品部只负责协调、追踪和验证完整性，不代替专业人员填写结论。

问题 27 已确认选择 A：高保真原型使用真实感模拟数据，并醒目标注“仅用于原型演示，未经专业审核”。模拟内容必须携带 `DEMO_UNREVIEWED` 与 `demoOnly: true`；真实计划发布需求必须阻止引用未审核内容。

问题 28 已确认选择 B：原型和后续开发使用两套完整模拟用户数据，分别贯穿减脂与增肌流程。产品接口需求以 `goalType`、计划版本和状态字段驱动分支，UI 不按用户身份或前端常量硬编码业务逻辑。

问题 29 已确认选择 A：首轮范围为双端关键闭环。H5 核心流程必须完整；Web 后台聚焦用户复核、饮食/训练审核与发布、周调整和异常处理；非核心后台不做完整交互。接口需求与验收优先覆盖该闭环。

### 任务 5：组织跨部门评审

**参与：**产品部、UI 部、研发团队、营养审核、训练审核、安全/隐私负责人。

**评审材料：**v2.0、原型、跨端产品行为、专业输入清单、验收矩阵、排期和风险清单。

**验收：**每个问题有负责人、决定、截止时间和变更记录；任何范围变更先更新产品规格，再进入设计或研发。

### 任务 6：定义封闭测试与发布门槛

**产品输出：**

- 6–10 名受邀用户的招募、纳入和排除标准；
- 四周有效执行定义及每周指标；
- 异常处理、运营值班和专业复核流程；
- 授权撤回、导出、删除/匿名化验收场景；
- 培训、测试账号、虚构数据、备份恢复和移动端兼容验收清单。

**验收：**专业签字、安全与权限验证、删除/匿名化演练、运营培训均完成后，才能启动真人封闭测试。

## 5. 当前产品决策

- 本期目标：6–10 名受邀健康成年人完成四周封闭测试；
- 产品形态：移动 H5 + Web 运营后台；
- 目标：仅减脂和增肌；
- 登录：受邀账号 + 密码；不接短信验证码或微信绑定；
- AI：首轮完全排除，不保留助手入口；
- 计划：饮食和训练分别审核；双审核后发布为用户可见的待确认计划，用户分别确认后才生效；任一用户拒绝进入已退回待修改且不得生效；
- 时限：同一用户仅一份待确认计划；确认截止为生效日前一天 20:00，超时不得生效；周调整只要改变计划内容就走完整新版本流程；
- 角色：运营、营养审核、训练审核、系统管理员、审计查看者五类；专业风险只能由对应专业审核者给出恢复结论；
- 留存：可识别用户数据在测试结束 30 天内删除或匿名化，导出包 7 天失效，备份最长滚动保留 30 天；
- 版本：已发布计划不可原地修改，同一日期只能有一份生效计划；
- 安全：风险、资料缺失或矛盾必须人工复核；红旗信号停止关联任务并创建高优先级事件；
- 调整：数据不足不得收紧能量目标、增加训练量或提高强度；
- 排除：公开注册、支付、AI、微信授权、短信验证码/邮件、媒体上传、设备、社交、商城、教练交易、医疗和康复；
- 数据：测试结束 30 天后删除或匿名化可识别数据；
- 内容：问题 27 选择 A，原型可用真实感模拟数据，但必须醒目标注且不得进入真人已发布计划。
- 模拟用户：问题 28 选择 B，减脂和增肌各使用一套完整数据，并由目标类型与计划版本驱动页面分支。
- 首轮范围：问题 29 选择 A，优先完成 H5 核心流程与 Web 复核、审核发布、周调整、异常处理闭环；非核心后台不做完整交互。
- 页面优先级：消息、数据请求、测试账号和审计为 P1 最小能力；内容管理、组织管理和指标大盘不做。
- 成功标准：至少 6 人开始、5 人完成四周、4 人达到有效执行，并同时满足反馈、调整采纳、价值、付费、安全、运营成本和数据权利演练门槛。

## 6. 下一决策点

产品部当前唯一优先事项是确认 v2.0 正式规格。规格确认后，依次进行页面需求冻结、跨端产品行为确认、专业输入签字和跨部门排期；产品部不进入接口设计、联调或代码开发阶段。
