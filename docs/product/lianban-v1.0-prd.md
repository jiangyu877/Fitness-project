## 2. 产品概述

### 2.1 产品定位

练伴为受邀健康成年人提供饮食与训练联动的四周封闭测试服务。用户不是领取一份固定计划，而是在执行、记录和每周人工调整中获得下一阶段的明确饮食与训练安排。

首轮验证的不是自动化处方能力，而是以下假设：

1. 用户能持续执行饮食与训练计划；
2. 用户能理解并采纳人工周调整；
3. 用户能感知饮食与训练联动的价值；
4. 用户愿意按明确价格继续使用。

### 2.2 服务边界

- 服务对象：18–60 岁、通过筛查的受邀健康成年人；
- 目标路线：仅减脂和增肌；
- 服务周期：每名测试用户连续四周；
- 产品形态：移动 H5 用户端 + 最小 Web 运营后台；
- 干预方式：计划、审核和调整由人工与经审核的结构化内容支持；
- 本期不是医疗服务、疾病营养、运动康复或正式商用服务。

### 2.3 北极星指标

四周有效执行用户数及有效执行率。

## 3. 目标与非目标

### 3.1 V1.0 目标

- 让符合条件的受邀用户完成授权、筛查、建档、计划确认、每日记录和周反馈；
- 让运营、营养审核者和训练审核者完成计划复核、发布、周调整和异常处理；
- 让计划状态、专业审核、用户确认、风险暂停和历史版本可追溯；
- 在四周测试结束后获得可解释的执行、安全、价值和付费意愿证据。

### 3.2 V1.0 明确不做

- V1.0 完全排除 AI；
- 公开注册、手机验证码、短信找回密码、微信登录或绑定；
- AI 助手、AI 对话、AI 生成、AI 调整、AI 审核、语音结构化、食物或动作识别；
- 支付、会员、社交、排行榜、挑战赛、商城、教练交易；
- 图片、视频、媒体上传，智能设备接入；
- 医疗诊断、疾病营养、药物建议、运动康复；
- 内容后台、员工组织后台、运营指标大盘和高级批处理的完整交互；
- 任何未经专业审核的内容用于真人计划。

## 4. 用户、角色与职责

### 4.1 用户端角色

| 角色 | 条件 | 主要能力 |
| --- | --- | --- |
| 受邀用户 | 运营预创建账号 | 登录、授权、筛查、建档、查看/确认计划、记录、反馈、数据请求 |
| 计划空档用户 | 没有当前生效计划 | 查看等待原因、历史、反馈和联系运营；不能执行计划任务 |
| 风险暂停用户 | 存在关联风险事件 | 查看影响范围、补充资料或联系运营；不能继续关联任务 |

### 4.2 员工角色

| 角色 | 能做 | 不能做 |
| --- | --- | --- |
| 运营人员 | 创建测试账号、用户沟通、整理草案、提交审核、发布待确认计划、执行流程通知 | 批准专业内容、解除专业风险 |
| 营养审核者 | 审核饮食内容与饮食相关风险 | 审核训练、管理账号、审核自己直接编制的饮食部分 |
| 训练审核者 | 审核训练内容与疼痛/恢复相关风险 | 审核饮食、管理账号、审核自己直接编制的训练部分 |
| 系统管理员 | 管理员工账号、角色、系统配置和应急停用 | 代替专业审核或业务批准 |
| 审计查看者 | 只读查看关键操作、授权、版本和异常处理 | 修改任何业务数据 |

同一自然人可以拥有多个角色，但每次操作必须记录当前角色和操作者。营养与训练是两个独立审核决定；具备双重资格的人可分别审核两部分，但不得审核自己直接编制的对应部分。风险恢复只能由具备对应专业资格的审核者决定，运营只负责通知与流程执行。

## 5. 端、范围与优先级

### 5.1 P0 用户端

- 受邀账号登录、首次修改密码、会话恢复；
- 知情说明、授权、筛查、人工复核、分阶段建档；
- 计划准备时间线、待确认计划、饮食与训练分别确认；
- 今日任务、饮食三态记录、训练逐组记录、训练事后补录、疼痛暂停；
- 周反馈、周调整说明、当前计划、历史计划；
- 风险阻断、人工处理和系统异常状态。

### 5.2 P0 Web 后台

- 工作台与待办队列；
- 共享用户详情；
- 计划草案、饮食审核、训练审核、发布待确认、拒绝处理和新版本；
- 周调整审核；
- 风险与异常队列及详情。

### 5.3 P1 最小能力

| 能力 | V1.0 最小范围 |
| --- | --- |
| 消息中心 | 列表、已读、跳转对应任务深链 |
| 数据导出/删除 | 用户提交和查看状态；后台接单、记录核验及处理结果 |
| 测试账号 | 创建、重置初始密码、解除锁定、停用 |
| 审计查询 | 只读核对关键操作，不做复杂报表 |

P1 不得阻塞 P0 原型验收，但数据权利、审计和账号操作的安全门槛仍必须在真人测试前满足。

## 6. 核心用户与员工流程

### 6.1 用户主流程

```text
受邀登录 -> 首次改密 -> 知情授权 -> 风险筛查
  -> 通过：分阶段建档 -> 计划准备
  -> 人工复核：补充资料/等待结论
  -> 明确排除：停止计划流程

计划准备 -> 双专业审核 -> 待确认计划
  -> 饮食与训练双确认 -> 等待生效 -> 当前计划
  -> 任一拒绝 -> 已退回待修改 -> 新版本重新审核
  -> 确认超时 -> 不得生效 -> 新版本或新生效日期

当前计划 -> 每日执行与记录 -> 周反馈 -> 人工周调整 -> 新计划版本
```

### 6.2 计划生命周期

| 状态 | 可见对象 | 下一步 |
| --- | --- | --- |
| 后台草案 | 运营及有权审核者 | 提交饮食与训练审核 |
| 审核中 | 对应审核者 | 双审核通过或退回修改 |
| 待确认计划 | 目标用户和有权员工 | 用户分别确认饮食与训练 |
| 等待生效 | 目标用户和有权员工 | 到计划生效时间成为当前计划 |
| 当前计划 | 目标用户和有权员工 | 每日执行、反馈或被新版本替代 |
| 已退回待修改 | 用户显示等待修改；后台可编辑新版本 | 创建新版本并重新审核 |
| 确认已超时 | 用户显示等待处理；后台可创建新版本 | 不得继续确认或自动生效 |
| 历史计划 | 只读 | 供解释与追溯 |

“发布”表示计划在双专业审核后对用户可见；“生效”表示计划成为当前执行版本。发布、用户确认和生效是三个独立节点。

### 6.3 确认时限与版本规则

1. 同一用户同一时刻最多存在一份待确认计划。
2. 每份待确认计划必须展示计划生效时间和确认截止时间。
3. 确认截止时间为计划生效日前一天 20:00，中国标准时间。
4. 运营最迟在确认截止前 24 小时发布待确认计划。
5. 截止前未完成双确认，版本进入确认已超时，不得自动生效或继续确认。
6. 已有当前计划时，新版本待确认、被拒绝或超时均不影响旧版本；旧版本仅执行到原结束时间。
7. 当前计划到期而没有新生效版本时进入计划空档，不静默延长旧计划，也不将待确认计划生成任务。
8. 初始计划被拒绝或超时且不存在旧版本时，用户端显示“暂无生效计划，团队正在处理”。
9. 已发布版本不可原地修改；任何业务含义变化必须创建新版本。
10. 改变饮食目标、训练内容、训练量、强度、频率或周期的周调整，完整复用双审核、发布待确认、用户双确认和到时生效流程。

### 6.4 每日执行与周反馈

- 今日页只展示当前计划生成的任务；待确认、超时、已退回或空档计划均不得生成可执行任务。
- 饮食记录采用按计划、部分偏离、明显偏离三态；偏离时再补充原因。
- 训练记录支持逐组记录和事后补录；疼痛立即暂停关联动作并进入安全处理路径。
- 周反馈收集执行、训练表现、睡眠、精力、饥饿、压力、恢复、疼痛和选填身体趋势。
- 数据不足时，系统和运营不得用“收紧能量、增加训练量或提高强度”作为调整结果；优先解决执行阻力，或保持核心计划。

### 6.5 风险与异常

- 筛查不通过、资料矛盾、疼痛、连续恢复不良和红旗信号均阻断关联流程；
- 风险状态必须展示影响范围、下一步和联系运营入口，不提供诊断结论；
- 红旗事件未获得专业恢复结论前，不得恢复关联任务；
- 系统失败、数据不足或版本冲突时，不展示半成品计划或覆盖历史数据；
- 所有关键状态变化必须可审计、可追溯。

## 7. 内容与专业审核

### 7.1 演示内容规则

高保真原型使用真实感模拟数据，但所有饮食、热量、动作、组次和周调整示例必须醒目标注：

> 仅用于原型演示，未经专业审核

模拟内容不得进入真人计划。两套模拟用户仅用于设计与测试验证：

- 减脂新手：29 岁女性，居家训练；
- 增肌新手：32 岁男性，商业健身房训练。

两套数据均覆盖建档、计划、七日执行、周反馈、周调整及异常变体。它们不是专业处方，也不能代表真人用户分布。

### 7.2 专业输入门槛

真人封闭测试前，必须由具名专业人员批准以下内容：

- 风险筛查题、排除条件、人工复核条件和资料矛盾规则；
- 红旗、疼痛、恢复不良的固定安全文案、恢复条件和响应时限；
- 饮食计划模板、字段、单位、食物示例、替换规则和调整边界；
- 训练计划模板、字段、单位、动作示例、替代、停止条件和调整边界；
- 最低数据充分性、调整顺序、单次变化边界和周调整示例；
- 内容来源、版本、审核人、复审日期和停用规则。

签字状态以 `docs/superpowers/specs/2026-07-23-professional-input-approval-checklist.md` 为准。签字前，任何部门不得自行补造专业阈值或处方。

## 8. 数据权利、隐私与审计

### 8.1 数据原则

仅收集当前服务、风险处理、必要审计和用户数据权利所需的信息。用户可提交导出或删除请求；系统必须记录授权、撤回、处理结果和例外。

### 8.2 留存口径

| 数据类别 | 测试结束后的处理 |
| --- | --- |
| 账号标识、联系方式、档案、筛查、身体数据、执行记录、反馈和原始计划版本 | 30 天内删除或不可逆匿名化 |
| 授权与撤回记录 | 最小化后保留 12 个月 |
| 审计记录 | 30 天内去标识化，去标识记录保留 12 个月 |
| 用户导出包 | 7 天后失效并删除 |
| 数据库备份 | 加密滚动保留，最长 30 天 |

用户删除请求在 7 个自然日内完成身份核验和处理说明。存在未关闭安全事件时，只冻结直接相关的最小记录，须告知延迟原因、记录具名批准；事件关闭后继续删除或匿名化。真人测试前必须完成隐私与合规复核，补足测试结束日、日志期限、汇总研究数据字段和安全冻结记录期限的实施细则。

### 8.3 审计要求

授权、筛查结论、计划版本、审核、发布、确认、超时、风险、恢复、导出、删除和账号安全等关键操作必须记录操作者、当前角色、对象、时间、版本、结果和请求标识。审计查看者只读，审计记录不可被业务操作覆盖。

## 9. 体验与可用性要求

### 9.1 体验原则

- 今日任务优先：先回答“今天做什么”；
- 安全优先：风险或异常时停止关联任务；
- 计划可解释：展示计划版本、变化、原因、生效时间和下周验证点；
- 轻量记录：先最小打卡，偏离或异常时再补充；
- 不羞辱用户：使用中性表达，不将偏离描述为失败或惩罚；
- 等待透明：说明当前阶段、影响范围、需要补充的内容和下一步；
- 历史不可覆盖：已发布、已生效内容只读，新变化通过新版本表达。

### 9.2 响应式与无障碍验收

- H5 必须在 360px、390px、430px 宽度可用，无文字溢出、控件遮挡或水平滚动；
- Web 必须在 1024px、1280px、1440px 宽度保持关键待办可用；低于 1024px 不提供复杂处理工作区；
- 以 WCAG 2.2 AA 为目标，具备键盘操作、可见焦点、语义标签、状态播报、错误摘要和模态焦点管理；
- 关键触控目标不小于 44 x 44px；支持 200% 缩放和减少动态效果；
- 至少人工验证 Chrome + 键盘、Edge + 键盘、Narrator + Edge。

完整页面矩阵包含 32 个唯一页面 ID，作为 UI 受控附件维护。PRD 正文不复制每页字段，避免与 UI 规格产生双重事实源。

## 10. 非功能产品要求

### 10.1 身份与安全

- 仅允许预创建的受邀账号使用账号和密码登录；首次登录必须修改初始密码；
- 用户与员工入口和会话隔离；员工 MFA、密码策略、会话时长、锁定阈值及重置核验必须在 G1 前由产品与安全共同批准；
- UI 显示权限和允许动作不能替代服务端权限；
- 未审核演示内容、未完成审核的计划、待确认计划和风险暂停任务均不得绕过发布或执行限制；
- 关键写操作须支持重复提交防护、版本冲突处理和可追溯审计。

### 10.2 质量与运维

- 用户、UI 和研发使用同一稳定状态语义；mock 与真实服务的可观察行为一致；
- 测试覆盖减脂、增肌、状态转换、权限、并发、风险、发布、恢复、数据权利和双端关键闭环；
- 生产发布前必须具备 HTTPS、备份恢复演练、错误追踪、风险逾期告警、发布回滚和运营手册；
- 技术方案可以调整，但不得以技术便利改变本 PRD 的产品规则。

## 11. 指标、埋点与四周测试判定

### 11.1 必测数据

- 招募、开始、完成和退出人数；
- 每日最小执行记录天数、饮食/训练完成情况及偏离原因；
- 周反馈提交、计划确认、调整理解和调整采纳；
- 风险事件、响应时间、暂停与恢复；
- 人工服务时间、用户价值反馈和价格意愿；
- 数据请求、删除/匿名化和恢复演练结果。

### 11.2 成功标准

满足下列全部条件，才建议进入下一阶段：

1. 至少 6 人正式开始测试，至少 5 人完成四周；
2. 至少 4 名完成者达到有效执行：四周中至少三周提交周反馈，且每周至少四天提交最小饮食或训练执行记录；
3. 全部应提交周反馈的总体提交率不低于 75%；
4. 已发布周调整的理解确认率不低于 80%，下一周实际采纳率不低于 60%；
5. 至少 4 名完成者明确认为饮食与训练联动优于割裂工具；
6. 至少 3 名完成者在给出统一价格方案后表示愿意继续付费，并记录理由与可接受价格；
7. 每名用户每周人工服务时间中位数不超过 45 分钟；
8. 不发生未关闭的严重安全事件，不存在绕过筛查、审核或风险暂停继续执行计划；
9. 授权撤回、导出、删除/匿名化各至少完成一次演练并留存证据。

指标统计定义、严重安全事件分级、调整理解确认方式和实际采纳判定方法，必须在真人测试启动前写入运营测试手册并经专业、隐私和产品负责人确认。
