# 练伴 V1.0 计划生命周期与执行隔离验收

版本：0.1  
日期：2026-07-25  
所有者：产品部  
状态：施工验收附件

本文细化 `docs/product/lianban-v1.0-prd.md` 中 P08-P10、P18 的可观察业务结果，不定义 API 地址、数据库结构、专业内容字段或调度实现。发生冲突时以 PRD 为准。

## 1. 本批范围

- 计划草案、饮食审核、训练审核、发布待确认、用户分别确认或拒绝、确认超时、等待生效、受控生效、替代和历史只读；
- 同一用户唯一待确认或等待生效版本、已发布版本不可原地修改、版本冲突和重复提交；
- 当前计划、历史计划和计划空档的真实持久化读取；
- 今日任务只允许来自当前生效计划；本批只验收任务生成阻断，不定义饮食、训练或周调整专业内容。

不在本批内批准筛查题、营养/训练数值、安全阈值、自动激活调度器、真人计划内容、部署环境或 G3 真人封测。

## 2. 生命周期结果

| 当前结果 | 用户可见结果 | 员工可见结果 | 禁止结果 |
| --- | --- | --- | --- |
| 草案或审核中 | 计划准备/等待 | 草案、对应审核任务和允许动作 | 用户看到半成品计划；未授权角色审核 |
| 双审核完成 | 仍等待发布 | 可发布或显示发布阻断项 | 单专业审核后发布 |
| 待确认 | 显示版本、生效时间、截止时间，饮食/训练分别确认或整版拒绝 | 显示两部分确认状态 | 生成今日任务；超过截止后继续确认 |
| 等待生效 | 明确“确认不等于立即生效” | 显示预定生效状态 | 客户端时间或读取请求触发生效 |
| 当前计划 | 显示当前版本和允许执行入口 | 显示当前版本与历史关系 | 多个当前版本；待确认版本生成任务 |
| 已退回或超时 | 显示团队处理中；旧计划存在时继续显示旧计划 | 创建新版本并重新审核 | 原版本继续确认、生效或原地修改 |
| 计划空档 | 显示“暂无生效计划，团队正在处理”，保留历史、反馈和联系运营 | 显示旧计划到期与待处理版本 | 静默延长旧计划；显示候选任务 |
| 历史计划 | 只读版本与替代关系 | 按权限只读追溯 | 覆盖、删除或把历史版本恢复为当前版本 |

## 3. 时间、版本与权限

- 确认截止时间为生效日前一天 20:00，中国标准时间；发布必须早于截止时间至少 24 小时。
- 任一确认发生在截止时间或之后时必须拒绝；超时版本不得继续确认或自动生效。
- 发布、双确认和生效是三个独立节点。生效只能由受信任、受审计的服务端动作完成；计划读取必须是纯读取。
- 已有当前计划时，新版本被拒绝或超时不得提前终止旧计划；旧计划只执行到原结束时间。
- 同一用户同一时刻最多存在一个待确认或等待生效版本；并发创建、发布或确认必须得到单一确定结果。
- 已发布版本不可原地修改。任何业务含义变化均创建新版本，重新完成双审核、发布、双确认和受控生效。
- 运营、营养审核者、训练审核者和用户只可执行 PRD 对应角色动作；审核者不得审核自己直接编制的对应部分。
- 客户端提交的操作者、角色、当前时间、计划归属或生效状态均不得作为可信授权事实。

## 4. 演示与真人隔离

- 未经专业审核的 fixture 必须持续显示“仅用于原型演示，未经专业审核”，并保持不可发布。
- 本地自动化可以使用虚构计划结构验证生命周期，但不得把测试注入解释为双专业批准或真人发布批准。
- 真人路由门禁未关闭时，真实账号计划写入、发布、确认、生效和任务生成必须零业务副作用拒绝，并保留结构化拒绝审计。
- UI 的真实 API 路径不得回退到 demo 计划、persona 或客户端本地状态机；未知或冲突状态进入联系运营/安全阻断。

## 5. 本批验收场景

| 编号 | 场景 | 必须结果 |
| --- | --- | --- |
| PL01 | 草案提交审核 | 进入审核中；用户仍只见计划准备；重复请求不新增版本 |
| PL02 | 饮食或训练单方审核通过 | 仍不可发布；对应审核者、角色和版本可追溯 |
| PL03 | 双审核通过并发布 | 仅生成一个待确认版本；显示生效时间和截止时间 |
| PL04 | 自审、错角色或跨用户操作 | 稳定拒绝、零业务副作用、单条可信主体拒绝审计 |
| PL05 | 用户只确认一部分 | 仍为待确认，不生成任务、不提前生效 |
| PL06 | 用户拒绝任一部分 | 整版退回待修改；原版本不能继续确认或生效 |
| PL07 | 截止前双确认 | 进入等待生效；读取和客户端时间不能激活 |
| PL08 | 截止时或之后确认 | 稳定拒绝并进入/保持确认超时；不得自动生效 |
| PL09 | 受信任动作按时生效 | 恰好一个当前计划；先前当前版本按规则成为历史 |
| PL10 | 新版本拒绝或超时且旧计划未到期 | 旧计划继续作为唯一当前计划，新版本不生成任务 |
| PL11 | 旧计划到期且无新版本生效 | 返回计划空档，不延长旧计划、不生成候选任务 |
| PL12 | 并发发布或重复确认 | 单一确定结果；幂等重放不产生重复审计或状态变化 |
| PL13 | 已发布版本修改 | 原版本保持不可变；业务变化只能创建新版本 |
| PL14 | 当前、历史和指定版本读取 | 权限过滤、历史只读、跨用户不可枚举；读取零状态副作用 |
| PL15 | 真人门禁未关闭 | 所有真人计划业务路由在业务执行前拒绝，拒绝可审计 |

## 6. 三部门交付证据

产品部只判定范围、状态语义、优先级和验收，不参与实现。

UI 部提交：真实服务状态驱动的待确认/等待生效/当前/空档/历史页面，双确认与拒绝交互，demo/真实隔离，错误恢复、键盘焦点和目标视口证据。不得在客户端实现审核、权限、超时或生效判定。

研发部提交：持久化生命周期、服务端权限、时间与版本规则、幂等/并发、纯读取、结构化审计、迁移升级和 OpenAPI/真实响应一致性证据。不得写入未批准的专业内容或把测试依赖当成真人审批。

联合验收必须至少包含减脂和增肌两条虚构路线、正常/拒绝/超时/空档/并发/越权分支，以及从真实 API 响应到 UI 状态的端到端证据。自动化测试通过不等于专业内容、生产环境或真人封测批准。
