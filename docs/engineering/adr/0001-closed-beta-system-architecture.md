# ADR-0001: 练伴封闭测试 MVP 系统架构建议

状态：建议方案，待产品基线冻结后批准
日期：2026-07-23
所有者：研发部

## 1. 决策范围

本文只定义技术结构和开工建议，不补充专业筛查、风险阈值、计划内容或周调整专业规则。产品基线 v1.1 已冻结状态、权限和留存口径；专业规则仍须由产品部和专业审核方签字后，通过版本化配置或明确的领域策略接入。

首轮目标是支持 6-10 名受邀用户的移动 H5 和最小 Web 后台，优先保证安全阻断、双专业审核、版本审计和可恢复性，不为尚未验证的规模提前拆分微服务。

## 2. 建议决策

采用模块化单体和单一关系数据库：

- 前端建议：TypeScript、React、Vite；H5 与 Web 后台分为两个应用，共享契约生成类型和基础组件，不共享页面业务状态。
- 后端建议：当前实施时仍处于维护期的 Node.js LTS、TypeScript、NestJS，按领域模块拆分。
- 数据库建议：托管 PostgreSQL，版本在开工时选择云厂商仍受支持的稳定版本。
- 迁移建议：使用支持显式 `up/down` 的 TypeScript 迁移工具；生产回滚优先前向修复，禁止依赖破坏性自动回滚。
- 接口建议：REST `/api/v1`；OpenAPI 3.1 为机器可读契约，生成前端类型和契约测试输入。
- 异步任务建议：首轮使用 PostgreSQL outbox + 独立 worker 进程处理到期生效、消息和异常任务，不引入 Redis 或消息队列。
- 文件存储：首轮无媒体上传，不建设对象存储；导出文件如启用，应短期生成、授权下载并按获批留存规则删除。
- 运行方式：容器化部署同一代码制品，Web API 与 worker 使用不同启动入口。

选择模块化单体是为了减少部署和一致性成本，同时保留清晰边界。只有在实际负载、团队规模或故障隔离证据出现后才拆分服务。

## 3. 模块边界

| 模块 | 责任 | 禁止事项 |
| --- | --- | --- |
| `auth` | 受邀账号、密码、会话、首次改密、锁定和退出 | 不决定用户是否符合健身服务条件 |
| `identity-access` | 五员工角色、资格、权限、字段可见性、允许动作 | 不以 UI 隐藏代替服务端授权，不允许对应内容自审 |
| `consent-profile` | 知情说明版本、分步档案和选填数据 | 不把选填字段升级为业务必填 |
| `screening-risk` | 保存已批准问卷结果、风险事件、暂停与恢复编排 | 不内置未批准阈值或诊断结论 |
| `plan` | 计划聚合、不可变版本、确认截止、超时、生效、空档和历史 | 不原地修改已发布版本，同一用户不得并存多个待确认版本 |
| `professional-review` | 营养/训练独立审核及退回 | 管理员不得代替专业审核 |
| `execution` | 今日任务、饮食三态、训练组次和恢复记录 | 待确认计划不得生成任务 |
| `weekly-adjustment` | 周反馈、事实、可信度、差异和完整新计划版本编排 | 不自行生成专业调整规则，不绕过双审核和双确认 |
| `work-queue` | 风险、审核、周调整和异常队列 | 不复制领域状态为第二事实源 |
| `messaging` | 站内消息和目标深链 | 消息快照不得决定目标页当前状态 |
| `content-governance` | demo/reviewed/published 内容状态和发布阻断 | 未审核 demo 内容不得真人发布 |
| `audit-privacy` | 追加式审计、导出/删除请求编排 | 不自行决定留存和删除例外 |

模块在同一进程内通过应用服务接口交互，禁止跨模块直接更新表。计划发布、确认超时、到期生效、风险暂停、任务生成和 outbox 事件必须处于同一数据库事务。

计划调度统一使用中国标准时间解释业务截止：确认截止为生效日前一天 20:00，发布不得晚于截止前 24 小时。超时版本进入终态并拒绝后续确认；当前计划只持续到原结束时间，之后显式进入无活动计划空档。

首轮员工角色固定为运营、营养审核、训练审核、系统管理员和审计查看者。同一自然人可以多角色任职，但每次操作记录当前角色；营养/训练审核者不得批准自己编制的对应部分，系统管理员不得代替专业审核。风险是否恢复只能由具备对应专业资格的审核者给出结论，运营只能执行通知和流程动作。具体风险阈值、暂停范围和响应 SLA 仍等待 P05 专业签字。

## 4. 环境与配置

建议四类环境：

| 环境 | 数据 | 用途 |
| --- | --- | --- |
| `local` | 纯虚构 seed | 本地开发和组件联调 |
| `test` | 每次重建的虚构数据 | 自动化测试 |
| `staging` | 虚构或明确授权的脱敏数据 | 双端验收、恢复演练 |
| `closed-beta` | 获同意的真实参与者数据 | 封闭测试，禁止调试后门 |

配置通过环境变量或云端密钥管理注入；仓库只提交示例键名，不提交密码、Cookie 密钥或生产连接串。环境间使用同一不可变制品，禁止在服务器直接改代码。

## 5. 部署建议

首轮建议采用一个托管 PostgreSQL、一个 API 容器、一个 worker 容器和静态前端托管。入口统一 HTTPS；H5 与 API 优先同站点部署以降低 Cookie、CORS 和微信内浏览器差异。若选择中国大陆节点，域名备案和云服务资质必须在排期中前置。

发布流程：构建 -> 单元/契约/迁移测试 -> staging 部署 -> smoke test -> 数据库备份点 -> closed-beta 滚动发布 -> 发布后验证。迁移必须在兼容旧应用的 expand 阶段先执行，应用稳定后再做 contract 清理。

## 6. 备份与恢复

技术上要求：

- 优先使用支持自动快照和时间点恢复的托管 PostgreSQL；
- 上线前执行一次完整恢复演练，记录恢复耗时和数据校验结果；
- 每次高风险迁移前创建可验证恢复点；
- 备份加密、访问最小化，恢复操作写审计；
- 备份滚动最长保留 30 天；删除请求涉及未关闭安全事件时，仅保留经具名批准的最小事件记录。

建议目标供产品评审：封闭测试阶段 RPO 不高于 24 小时、RTO 不高于 4 小时。未获批准前，这只是容量和成本估算输入，不是承诺。

## 7. 监控与运维

最低可观测性：

- 结构化 JSON 日志，包含 `requestId`、环境、模块、错误码和脱敏主体 ID；
- API 延迟、错误率、登录失败、队列积压、逾期任务、worker 失败、数据库连接和备份状态指标；
- 发布失败、计划计算失败、风险事件未接单、消息投递失败和备份失败告警；
- 健康检查区分存活与就绪，worker 提供心跳；
- 审计日志与应用调试日志分离，禁止记录密码、会话令牌、筛查答案全文或自由文本敏感内容。

告警接收人、值班时间、风险响应 SLA 和日志保留期由产品/运营/安全共同批准。

## 8. 安全基线

- 密码使用经安全评审的自适应哈希算法，建议 Argon2id；禁止可逆加密。
- 用户与员工使用独立会话域；Cookie 采用 `HttpOnly`、`Secure` 和合适的 `SameSite`，写操作具有 CSRF 防护。
- 登录、重置、审核、发布、导出和删除接口实施速率限制、幂等和审计。
- 服务端执行 RBAC、字段级授权和对象所有权校验；所有拒绝返回稳定错误码。
- 生产禁止 demo 身份切换、调试后门和未审核内容发布。
- 依赖锁定、自动漏洞扫描、密钥轮换和最小数据库权限进入发布门槛。
- 员工 MFA、会话时长、密码策略和锁定阈值需要产品与安全批准后落地。

## 9. 数据生命周期映射

- 可识别账号、档案、筛查、身体、执行、反馈和原始计划版本：测试结束后 30 天内删除或不可逆匿名化。
- 授权/撤回记录：最小化后保留 12 个月。
- 审计：30 天内对用户标识去标识化，去标识记录保留 12 个月。
- 用户导出包：生成 7 天后失效并删除。
- 数据库备份：加密滚动保留，最长 30 天。

删除请求原则上 7 个自然日内完成身份核验和处理说明。具体字段级实现仍须通过三方技术映射及真人测试前隐私/合规复核。

## 10. 被否决的替代方案

- 微服务：首轮规模不足以抵消分布式事务、部署和观测成本。
- Firebase/无模式数据库作为主存储：不利于计划版本、双审核、审计和强一致约束。
- 直接在前端 mock 中实现业务规则：会造成真实 API 与原型状态漂移。
- 首轮引入 Redis/消息队列：当前没有吞吐证据，PostgreSQL outbox 足够且更易恢复。

## 11. 批准前依赖

本 ADR 获批不等于业务开工。产品 v1.1 已冻结状态、权限和留存口径，但仍待三方技术映射；核心实现继续依赖专业规则签字、部署地域/预算、认证安全参数和 UI 规格冻结。
